# TGE-ADM-01 — Admin Portal Scope and Contracts

**Status:** Discovery baseline; decisions marked open require TGE policy approval before implementing the affected operation.  
**Design authority:** The 36 supplied admin design references under `TGE UI/Admin Pages` and the supplied admin-design PDFs. Screen structure, fields, and actions are the target behavior. Names, counts, charts, timestamps, and records shown in mockups are illustrative and are not production data. This inventory does not authorize inventing data or presenting mock values as live.

## Objective and boundary

Map the admin screen references to current frontend routes, backend endpoints, permission grants, persisted models, validation and status behavior, audit needs, and cross-surface effects. Record gaps for later implementation. This task does not implement the admin portal, database migrations, API routes, or policy decisions.

Admin frontend routes and admin controllers are not present in the current repository. Proposed routes and endpoints below are contracts to implement in later scoped tasks; they are not existing APIs. The server is an Express modular monolith, with feature modules organized into domain/application/presentation/infrastructure layers. The client uses Next App Router and feature modules under `client/src/modules`.

## Current platform contracts

### Authorization

Protected requests require an active, non-deleted user and a server-side role permission grant. `requirePermission` looks up the grant from `RolePermission`; client-side route hiding is not authorization. Seeded permissions relevant to these designs are:

| Area | Existing permission codes | Seeded roles |
| --- | --- | --- |
| Account and role administration | `users.manage`, `roles.manage` | System Administrator; Organisation Administrator has `users.manage` only |
| Members | `members.manage` | System Administrator; Organisation Administrator |
| Programmes/cohorts | `programmes.manage`, `programmes.deliver` | System Administrator; Organisation Administrator; Trainer/Facilitator has delivery only |
| Events | `events.manage`, `events.read` | System Administrator; Organisation Administrator |
| Resources | `resources.manage`, `resources.read` | System Administrator; Organisation Administrator; Mentor and Trainer/Facilitator have manage |
| Mentorship | `mentorship.manage`, `mentorship.read`, `assigned-members.read` | System Administrator; Organisation Administrator; Mentor has mentorship/manage and assigned-members/read |
| Reports | `reports.view` | System Administrator; Organisation Administrator |
| Website content | `website.manage` | System Administrator; Organisation Administrator |
| Settings/audit | `system.manage`, `audit.view` | System Administrator only |

These grants are a baseline, not a screen-by-screen policy approval. The existing admin operations are not mounted as routes and have no implemented endpoint-level permission/field-level contracts. Future operations must enforce permissions on the server. Whether Organisation Administrators may view or edit roles/settings/audit, and whether permissions should be split more finely, remains an open decision.

### Existing persisted records and status vocabulary

| Concept | Existing record(s) | Current status / limitation |
| --- | --- | --- |
| User account | `User`, `Role`, `Permission`, `RolePermission`, activation/reset/revoked-token records | `User.status`: `PENDING_ACTIVATION`, `ACTIVE`, `SUSPENDED`, `DEACTIVATED`; deletion is separately represented by `deletedAt`; email verification by `emailVerifiedAt`. Do not use membership status as account status. |
| Membership application | `MembershipApplication` | Enum: `PENDING`, `APPROVED`, `REJECTED`; reviewer/time and rejection reason are persisted. This is not an account or membership status. |
| Member | `Member` | `membershipStatus` is free-form `String` (default `active`), with `membershipNo` and `joinedAt`. No approved membership status enum/workflow exists. Do not assume UI labels `Pending Approval`, `Inactive`, or `Alumni` map to account or application states. |
| Programme/cohort participation | `Programme`, `Cohort`, `Enrollment`, assignments | Programme, cohort, enrollment and assignment statuses are free-form strings. `Enrollment.status` defaults to `enrolled`; `completedAt` is separate. No canonical transition rules. |
| Event | `Event`, `EventRegistration`, `EventStaffAssignment`, `EventMedia` | Event status is free-form; public endpoint currently treats `published` as visible and registration-open when upcoming/deadline/capacity allow. Registrations separately have `registrationStatus` and `attendanceStatus`. |
| Business listing/review | `Business`, category assignments, `BusinessReview`, media | `Business.status` (operational) and `publicationStatus` (public visibility) are separate free-form fields. Public listings require `active` + `approved`. `BusinessReview.reviewStatus` is another separate free-form state; review history can be multiple rows. |
| Resource | `Resource`, `ResourceVersion`, category and programme/cohort joins | Resource status is free-form; member reads require `published` and `publishedAt <= now`; audience is access level plus programme/cohort assignments. |
| Mentorship | `Mentor`, `MentorAssignment`, `MentoringSession`, `MentoringObjective`, progress records | Statuses are free-form. Progress records persist note/value/recorder/time. No approved enum or transitions. |
| Website content | `Page`, `News` | Status is free-form; public news requires `published` and `publishedAt <= now`. Page public delivery contract is not established in the current public module. |
| Communication | `Announcement`, target joins, `Notification`, `CommunicationDelivery` | Announcement and delivery states are free-form. Member notification read state uses `readAt`. Delivery providers/channels and scheduling policy are not established here. |
| Audit/configuration | `AuditLog`, `SystemSetting` | Audit model stores actor/action/entity/details/IP/time. Only auth and member profile/photo flows currently write audit entries; admin mutation coverage is absent. Settings are JSON key/value records; editable keys/schema are not defined. |

All of these are distinct state domains. In particular, **account status ≠ membership application status ≠ membership status ≠ publication status ≠ business review status**. Event registration and attendance status are also separate. No admin UI may collapse these into one generic status field.

### Current route surface

The app mounts public routes under `/api/public`, auth and account routes under `/api/auth`, and member routes under `/api/member`. Current member routes cover dashboard, profile/photo, programmes, events/details, mentorship, resources/files, businesses, notifications/read, conversations/messages and call signals. Public routes include home previews, programmes, events/details/registration/gallery, news, approved business directory, and business categories/details. There are no admin routes or admin frontend pages in `client/src/app` or `server/src/app.module.ts`.

## Cross-surface data and status rules

1. Admin writes use the existing canonical records where those records match the design. Admin screens must not maintain parallel copies of member, event, programme, business, resource, mentorship or website data.
2. A publication change is observable: programme publication affects `/programmes` and member programme discovery; event publication affects public `/events`, gallery eligibility, and member events; resource publication/targeting affects member resources; business approval plus active state affects public business directory/home previews and member business status; news publication affects public News/home previews; announcements/notification writes affect member notifications if included in eventual admin scope.
3. Identity edits to fields shared with the member profile must be reflected by both routes. Account activation/suspension/deactivation is an authorization change. Membership approval creates/updates membership separately from account activation; the approved orchestration is not yet specified.
4. Public DTOs are deliberately bounded: event public details omit meeting link, capacity, staff, registration and creator; programme public DTO omits cohorts/enrollments; business/news use explicit public-safe fields. Admin detail data must not be reused as an anonymous DTO.
5. Every mutation should record actor, action, entity and outcome in AuditLog; sensitive fields, passwords, token values, private meeting links, and full message content should not be copied into audit details. Exact event taxonomy and retention are open.

## Unresolved policy decisions

- D1 — Who may create member records, approve applications, issue membership numbers, and activate accounts? Are approval and account activation one or separate decisions?
- D2 — Canonical membership states, including the meaning and transition rules for pending approval, active, inactive, suspended, and alumni; whether alumni retain portal access.
- D3 — Permission matrix by role and operation, including Organisation Administrator, mentors/trainers, business review, support, audit, settings, export, role grants, and self-administration.
- D4 — Canonical allowed status values/transitions for programmes, cohorts, enrollment, events, event registration/attendance, resources, mentorship, businesses/reviews, pages/news, announcements and support.
- D5 — Business-review policy: reviewer eligibility, approve/reject reasons, revision/resubmission, appeal, multiple reviewers, and whether public visibility requires both active and approved (current public contract says yes).
- D6 — Progress definitions and authoritative sources for programme participant progress, mentorship objective progress, dashboard metrics and profile-completion percentage.
- D7 — PII/privacy policy for member profile details, guest event attendees, business contacts, exports, profile photos, support enquiries, and audit detail/retention.
- D8 — Content publication policy: page routes/templates, safe rich-text formats, preview, scheduled publication, unpublish, archive, rollback, and who can publish.
- D9 — Support handling and system settings contract, including whether existing ContactEnquiry is sufficient, who responds, outbound channel/provider, and retention.
- D10 — File/media requirements: max size/types, malware scanning, storage provider, photo consistency, resource version activation, and public media approval.
- D11 — Event policy: event cancellation, registration closing separate from publication, capacity changes after registrations, attendance correction and guest/member duplicate resolution.
- D12 — Reporting period/timezone, historical snapshots versus live aggregation, definitions of active members/businesses and completed participation, and audit of exports.

## Implementation handoff

TGE-ADM-01 is complete as a discovery artifact. Before implementing a screen, resolve the decisions and gaps that gate that feature, then define the endpoint payload, validation and transition matrix in its implementation ticket. Follow the existing modular-monolith/Clean Architecture server pattern and feature-sliced client pattern from the TGE Development Standards; add migrations only for approved genuine data gaps. Admin operations that mutate shared records must be checked against their public/member readers and preserve bounded public DTOs.
